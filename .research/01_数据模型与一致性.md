# 数据模型与一致性 - Riak Core 的分布式数据思维

> 📖 **对应DDIA章节**: 第五章《复制》中的"处理写入冲突"与第六章《分区》中的"一致性保证"

## 🎯 核心问题：当多个节点同时修改同一数据时，如何判定"谁是正确的"？

想象一个场景：你有一个用户购物车，用户在北京和上海同时添加了不同的商品。两个数据中心各自记录了操作，当网络恢复同步时，应该以谁为准？

### 传统数据库的答案：**"我替你决定"**
- 使用锁机制，只有一个节点能写入
- 或者用"最后写入胜利"(LWW)，时间戳最新的获胜
- **问题**：要么性能差（锁等待），要么丢数据（时间戳不准）

### Riak Core 的答案：**"记录一切，让应用决定"**

---

## 🧪 实验一：向量时钟 (Vector Clock)

### 概念理解

想象你在记录一个"多人协作文档"的修改历史：

```
 Alice 说："我修改了第1次"
   Bob 说："我修改了第1次"
 Alice 又说："我修改了第2次"
```

向量时钟就是给每个修改者发一个"计数器"：

```erlang
%% 文件: src/vclock.erl

%% 向量时钟的数据结构非常简单
-type vclock() :: [dot()].
-type dot() :: {vclock_node(), {counter(), timestamp()}}.

%% 例如：
%% [{alice, {2, 1234567890}}, {bob, {1, 1234567895}}]
%% 含义：alice修改了2次，bob修改了1次
```

### 关键操作

#### 1. 创建新时钟
```erlang
%% 从零开始
fresh() -> [].

%% 带初始值创建
fresh(Node, Count) ->
    [{Node, {Count, timestamp()}}].
```

#### 2. 判断因果关系 - 核心算法

```erlang
%% 判断 Va 是否"继承"自 Vb
%% 即：Va 是否包含 Vb 的所有历史
-spec descends(Va :: vclock(), Vb :: vclock()) -> boolean().
descends(_, []) ->
    % 所有向量时钟都"继承"自空时钟
    true;
descends(Va, Vb) ->
    [{NodeB, {CtrB, _T}}|RestB] = Vb,
    case lists:keyfind(NodeB, 1, Va) of
        false ->
            false;  % Va 没有记录 NodeB 的修改，不可能继承
        {_, {CtrA, _TSA}} ->
            % 关键：Va中NodeB的计数器必须 >= Vb中的
            (CtrA >= CtrB) andalso descends(Va, RestB)
    end.
```

**直观理解**：如果 Alice 的时钟显示 `[alice:2, bob:1]`，而 Bob 的时钟显示 `[bob:1]`，那么 Alice 的时钟"包含" Bob 的历史，因为 Alice 记录了 Bob 的修改。

#### 3. 合并时钟 - 并发版本的"握手"

```erlang
%% 合并多个向量时钟，取每个节点的最大计数
-spec merge(VClocks :: [vclock()]) -> vclock().
merge([])             -> [];
merge([SingleVclock]) -> SingleVclock;
merge([First|Rest])   -> merge(Rest, lists:keysort(1, First)).
```

**示例**：
```
时钟A: [alice:2, bob:1]  (Alice 修改了2次，见过 Bob 的1次修改)
时钟B: [alice:1, bob:2]  (Bob 修改了2次，见过 Alice 的1次修改)

合并后: [alice:2, bob:2]  (双方都修改了2次，记录完整历史)
```

### 判定规则总结

| 情况 | 判定 | 含义 |
|------|------|------|
| `descends(A, B) = true` | A 继承 B | A 是 B 的"后代"，A 更新 |
| `descends(B, A) = true` | B 继承 A | B 更新 |
| `descends(A, B) = false` 且 `descends(B, A) = false` | **并发冲突** | 两者互不知情，需要合并 |

## 🧪 实验二：点版本向量 (Dotted Version Vectors - DVVSet)

### 为什么需要 DVVSet？

向量时钟有个问题：**无法区分"相同的值"和"并发写入相同的值"**。

```
场景：
1. Alice 写入 "hello" → 时钟 [alice:1]
2. Bob 读取后写入 "hello" → 时钟 [bob:1]（不知道 Alice 写过）
3. 系统看到两个相同的 "hello"，但时钟并发

用传统 VC：无法区分这和"两个用户同时写入 hello"的区别
用 DVVSet：可以精确识别 Bob 的 "hello" 是基于 Alice 的版本
```

### DVVSet 的核心改进

```erlang
%% 文件: src/dvvset.erl

%% DVVSet 的数据结构
-type clock() :: {entries(), values()}.
-type entries() :: [{id(), counter(), values()}].
                      %% 节点ID   计数器    该节点产生的值列表

%% 关键区别：每个"dot"（点）都携带了具体的值
%% 而不是像 VC 那样只记录计数器
```

### 核心操作

#### 创建与更新
```erlang
%% 创建新的 DVVSet
new(Vs) when is_list(Vs) -> {[], Vs};
new(V) -> {[], [V]}.

%% 更新：推进因果历史
update({Cc, [V]}, I) -> 
    {event(C, I, V), []}.

%% 新值被记录在对应的"dot"中
event([], I, V) -> [{I, 1, [V]}];
event([{I, N, L} | T], I, V) -> [{I, N+1, [V | L]} | T].
```

#### 同步合并
```erlang
%% 同步多个 DVVSet，保留所有因果信息
sync(L) -> lists:foldl(fun sync/2, {}, L).

sync(C1={E1,V1}, C2={E2,V2}) ->
    V = case less(C1, C2) of
        true  -> V2;                    %% C1 被包含，取 V2
        false -> case less(C2, C1) of
                    true  -> V1;        %% C2 被包含，取 V1
                    false ->            %% 并发！保留所有值
                        sets:to_list(sets:from_list(V1++V2))
                 end
    end,
    {sync2(E1,E2), V}.
```

### 实际例子：购物车冲突解决

```
初始：购物车为空 []

操作1 (Alice): 添加 iPhone → [iPhone]
操作2 (Bob):   添加 iPad   → [iPad]
               (Bob 没看到 Alice 的操作)

同步时：
- 传统 VC: 需要应用层决定如何合并
- DVVSet: 自动保留两个值 → [iPhone, iPad]
          并标记为并发产生的 siblings（兄弟）
```

## 🧪 实验三：时钟剪枝 (Clock Pruning)

### 问题：向量时钟会无限增长吗？

理论上会！如果集群中有 1000 个节点，每个节点都修改过数据，向量时钟就有 1000 个条目。

### Riak Core 的解决方案：智能剪枝

```erlang
%% 文件: src/vclock.erl

-spec prune(V::vclock(), Now::integer(), BucketProps::term()) -> vclock().
prune(V, Now, BucketProps) ->
    %% 1. 按时间戳排序（最老的在前）
    SortV = lists:sort(fun({N1,{_,T1}},{N2,{_,T2}}) -> {T1,N1} < {T2,N2} end, V),
    prune_vclock1(SortV, Now, BucketProps).

prune_vclock1(V, Now, BProps) ->
    %% 2. 如果时钟很小，保留全部
    case length(V) =< get_property(small_vclock, BProps) of
        true -> V;
        false ->
            %% 3. 如果时钟很"年轻"，保留全部
            {_,{_,HeadTime}} = hd(V),
            case (Now - HeadTime) < get_property(young_vclock,BProps) of
                true -> V;
                false -> prune_vclock1(V, Now, BProps, HeadTime)
            end
    end.

prune_vclock1(V, Now, BProps, HeadTime) ->
    %% 4. 否则，移除最老的条目
    case (length(V) > get_property(big_vclock,BProps)) orelse
         ((Now - HeadTime) > get_property(old_vclock,BProps)) of
        true -> prune_vclock1(tl(V), Now, BProps);  %% 递归剪枝
        false -> V
    end.
```

### 剪枝策略图解

```
配置参数：
- small_vclock: 50    (少于50条不剪)
- young_vclock: 3600s (1小时内不剪)
- big_vclock: 100     (超过100条必剪)
- old_vclock: 86400s  (超过1天必剪)

时间线：
  ┌─────────────────────────────────────────────────────┐
  │ [Node1:1h前] [Node2:2h前] [Node3:3h前] ... [Node100:刚写入] │
  └─────────────────────────────────────────────────────┘
       ↑ 剪掉这些老条目                        ↑ 保留新条目
```

## 🎨 一致性模型选择指南

### Riak Core 提供的工具箱

| 需求 | 推荐方案 | 代码模块 |
|------|----------|----------|
| 最终一致性 + 自动合并 | 向量时钟 | `vclock.erl` |
| 精确因果关系追踪 | DVVSet | `dvvset.erl` |
| 应用自定义合并 | 使用 `reconcile/2` | `dvvset:reconcile/2` |
| 最后写入胜利 (LWW) | 使用 `lww/2` | `dvvset:lww/2` |

### 代码示例：自定义合并策略

```erlang
%% 使用"最大值"策略合并数值
merge_max(Clock) ->
    F = fun(Values) -> lists:max(Values) end,
    dvvset:reconcile(F, Clock).

%% 使用"时间戳最新"策略 (LWW)
merge_lww(Clock) ->
    F = fun({_, TS1}, {_, TS2}) -> TS1 =< TS2 end,
    dvvset:lww(F, Clock).
```

## 🔬 深度分析：为什么 Riak 选择这种模型？

### 1. CAP 定理的权衡

```
        CAP 定理
           │
    ┌──────┼──────┐
    │      │      │
  一致性  可用性  分区容错
    │      │      │
    └──┬───┴──┬───┘
       │      │
   Riak 选择: AP
   (牺牲强一致性，换取高可用)
```

### 2. 实际场景考量

| 场景 | 强一致性 | 最终一致性 (Riak) |
|------|----------|-------------------|
| 银行转账 | ✅ 必须 | ❌ 不适合 |
| 社交媒体点赞 | ⚠️ 可选 | ✅ 更适合 |
| 购物车 | ⚠️ 可选 | ✅ 更适合 |
| 配置管理 | ✅ 推荐 | ⚠️ 可选 |

### 3. 性能优势

```erlang
%% 写入操作只需要本地成功
%% 不需要等待其他节点确认
write(Key, Value) ->
    LocalVC = vclock:increment(node(), get_vc(Key)),
    store_locally(Key, Value, LocalVC),
    async_replicate_to_other_nodes(Key, Value, LocalVC),
    ok.  %% 立即返回！

%% 读取操作可以配置一致性级别
read(Key, R) ->
    %% R = 需要读取的副本数
    %% R=1: 快但可能旧
    %% R=all: 慢但最新
    Values = read_from_R_nodes(Key, R),
    resolve_conflicts(Values).
```

**Riak 的回答**:

    true ->

    false ->
        store(Key, newer_value(VC1, VC2, Value1, Value2))
end.
